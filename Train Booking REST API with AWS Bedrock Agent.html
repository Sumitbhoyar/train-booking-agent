Architect-Level Interview Questions & Answers

Train Booking REST API with AWS Bedrock Agent

1. System Architecture & Design

Q1.1: Walk me through the overall architecture of this system. Why did you choose this architecture pattern?

Answer:
This is a serverless event-driven architecture with two primary components:

  1. REST API Layer - API Gateway HTTP API → Lambda (FastAPI container)
  2. Conversational AI Layer - Amazon Bedrock Agent → Action Group Lambda

Architecture Rationale:

  • Serverless-first approach: Eliminates infrastructure management, provides automatic scaling, and reduces operational overhead
  • Separation of concerns: REST API serves direct programmatic access, while Bedrock Agent provides natural language interface
  • Event-driven: API Gateway triggers Lambda on-demand, Bedrock Agent invokes action group functions as needed
  • Container-based Lambda: FastAPI with all dependencies packaged in Docker provides consistency across environments and supports complex dependencies like ReportLab for PDF generation
  • HTTP API over REST API: Chose API Gateway v2 (HTTP API) for 71% cost savings and lower latency compared to REST API v1

Data Flow:

User → API Gateway → Lambda (FastAPI/Mangum) → In-Memory DB
User → Bedrock Agent (Claude) → Action Group Lambda → Shared In-Memory DB

The architecture follows AWS Well-Architected Framework principles: operational excellence (IaC with CDK), security (IAM roles with least privilege), reliability (managed services), performance efficiency (serverless scaling), and cost optimization (HTTP API, right-sized Lambda).

Q1.2: Explain the purpose of using Mangum in this architecture. What problem does it solve?

Answer:
Mangum is an ASGI-to-AWS Lambda adapter that bridges the gap between FastAPI (an ASGI application) and AWS Lambda’s event model.

Problem it solves:

  • Protocol mismatch: FastAPI expects ASGI (Asynchronous Server Gateway Interface) requests, but Lambda receives API Gateway events in JSON format
  • Event transformation: Mangum converts API Gateway v2 Payload Format events into ASGI scope dictionaries that FastAPI understands
  • Response conversion: Transforms ASGI responses back into Lambda-compatible response format

Implementation in our project:

from mangum import Mangum
handler = Mangum(app, lifespan="off")

Key configuration:

  • lifespan="off": Disables ASGI lifespan events since Lambda manages the application lifecycle
  • Supports PayloadFormatVersion.VERSION_2_0 for HTTP API

Alternatives considered:

  • AWS Lambda Web Adapter (requires additional sidecar)
  • Custom adapter (higher maintenance)
  • API Gateway REST API with proxy integration (higher cost)

Mangum was chosen for its maturity, zero-dependency approach, and excellent FastAPI compatibility.

Q1.3: Why did you choose to deploy FastAPI as a Docker container instead of a traditional Lambda deployment package?

Answer:
Container-based deployment provides several advantages for this use case:

1. Complex Dependencies:

  • ReportLab (PDF generation) has native dependencies and specific build requirements
  • Multiple Python packages (FastAPI, Pydantic, Mangum) with their dependencies
  • Docker ensures consistent builds across development and production environments

2. Size & Flexibility:

  • Lambda deployment packages limited to 50MB (250MB unzipped)
  • Container images support up to 10GB, providing headroom for future features
  • Our current image is ~500MB with all dependencies

3. Development-Production Parity:

  • Same Dockerfile used for local development and AWS deployment
  • “Build once, run anywhere” eliminates environment-specific issues
  • Developers can test exact production environment locally

4. Easier Dependency Management:

  • Complex build steps handled in Dockerfile
  • No need for Lambda Layers or complex packaging scripts
  • CDK handles ECR push and Lambda deployment automatically

Trade-offs:

  • Cold start: Container images have 1-3 second cold starts vs. 200-500ms for zip packages
  • Build time: Docker builds take longer than pip install
  • Storage: ECR storage costs (minimal for our use case)

Mitigation:

  • Provisioned concurrency can be added for latency-sensitive workloads
  • Multi-stage builds could reduce image size further
  • For this use case, cold starts are acceptable (not user-facing real-time API)

2. AWS Services & Cloud-Native Design

Q2.1: Compare HTTP API (v2) vs REST API (v1) in API Gateway. Why did you choose HTTP API?

Answer:
Detailed Comparison:

Feature HTTP API (v2) REST API (v1)
Cost $1.00 per million requests $3.50 per million requests
Latency Lower (optimized for speed) Higher
WebSocket Not supported Not supported (separate API)
Authorization JWT, OAuth 2.0, IAM, Lambda Cognito, IAM, Lambda, API Keys
Request Validation Limited Full OpenAPI validation
Usage Plans Not supported Supported (throttling, quotas)
Edge Optimization Regional only Regional, Edge, Private
API Keys Not supported Supported

Why HTTP API for this project:

  1. Cost Efficiency (71% savings)

    • Train booking is cost-sensitive
    • No complex authorization requirements
    • Estimated savings: $2.50 per million requests

  2. Performance

    • Lower latency for simple proxying to Lambda
    • Optimized for serverless backends

  3. Sufficient Features

    • CORS support ✓
    • Lambda proxy integration ✓
    • CloudWatch logging ✓
    • Don’t need: API keys, usage plans, request validation

  4. Simpler Configuration

    • Less boilerplate in CDK
    • Faster deployments

When to use REST API instead:

  • Need API keys or usage plans for rate limiting per customer
  • Require request/response transformation
  • Need edge-optimized global distribution
  • Require AWS WAF integration (possible with HTTP API but better with REST)

Q2.2: Explain how AWS Bedrock Agent works and how it integrates with your action group Lambda. What are the advantages over building a custom chatbot?

Answer:
AWS Bedrock Agent Architecture:

  1. Orchestration Layer (Managed by AWS):

    • Natural language understanding via Claude 3.5 Sonnet v2
    • Intent detection and slot filling
    • Multi-turn conversation management
    • Context retention (session TTL: 10 minutes)

  2. Action Groups (Developer-defined):

    • OpenAPI schema defines available tools
    • Lambda function implements tool logic
    • Bedrock Agent determines when to invoke tools

  3. Tool Use Pattern:

User: "Book me a train from Paris to Lyon tomorrow"
  ↓
Agent: [Analyzes intent] → Needs searchTrains + createBooking
  ↓
Agent: [Invokes] searchTrains(Paris, Lyon, 2025-12-28)
  ↓
Lambda: Returns available trains
  ↓
Agent: [Asks user] "Which train? Also need name and email"
  ↓
User: "T101, John Doe, john@example.com"
  ↓
Agent: [Invokes] createBooking(T101, John Doe, john@example.com, 2025-12-28)
  ↓
Agent: [Natural language response] "Booked! Your booking ID is BK12345678"

Integration with Action Group Lambda:

  • AWS Lambda Powertools BedrockAgentResolver: Simplifies routing
  • Decorators: @app.get("/searchTrains"), @app.post("/createBooking")
  • Automatic parsing: Extracts parameters from agent invocations
  • Structured responses: Returns JSON that agent converts to natural language

Advantages over custom chatbot:

  1. No ML/NLP Expertise Required

    • AWS manages model training, prompt engineering, RAG
    • Automatic intent detection and entity extraction

  2. Built-in Orchestration

    • Multi-step workflows handled automatically
    • Context management across conversation turns
    • Tool chaining and dependency resolution

  3. Enterprise Features

    • Audit logging via CloudWatch
    • IAM-based security
    • Knowledge base integration (optional)
    • Guardrails for content filtering

  4. Time to Market

    • Built in days, not months
    • No training data required
    • Just define OpenAPI schema and implement functions

  5. Cost Effective

    • Pay per token, no infrastructure
    • No model hosting costs
    • Uses latest Claude models automatically

Trade-offs:

  • Less control over conversation flow
  • Limited to supported models
  • AWS region availability constraints
  • Vendor lock-in

Q2.3: How would you modify this architecture to support production-grade persistence? What AWS services would you use?

Answer:
Current Limitation: In-memory storage (Python dictionaries) resets on Lambda cold starts and doesn’t support concurrent bookings.

Production Architecture with Persistence:

Option 1: DynamoDB (Recommended for this use case)

# Table Design
Trains Table:
  PK: train_number (String)
  Attributes: name, route, departure_time, available_seats
  GSI: route_index (from#to)

Bookings Table:
  PK: booking_id (String)
  Attributes: train_number, passenger_name, email, journey_date, 
              seat_number, status
  GSI: email_index (for user lookup)
  GSI: train_date_index (train_number#journey_date for seat management)

Implementation Changes:

import boto3
dynamodb = boto3.resource('dynamodb')
bookings_table = dynamodb.Table('train-bookings')

def create_booking(train_number, passenger_name, email, journey_date):
    # Check seat availability with atomic counter
    response = bookings_table.update_item(
        Key={'booking_id': booking_id},
        UpdateExpression='SET available_seats = available_seats - :decr',
        ConditionExpression='available_seats > :zero',
        ExpressionAttributeValues={':decr': 1, ':zero': 0},
        ReturnValues='UPDATED_NEW'
    )

Benefits:

  • Fully managed, serverless
  • Single-digit millisecond latency
  • Automatic scaling (on-demand mode)
  • DynamoDB Streams for event-driven workflows
  • Point-in-time recovery
  • Global tables for multi-region

Cost: ~$1.25 per million read/write requests (on-demand)

CDK Implementation:

bookings_table = dynamodb.Table(
    self, "BookingsTable",
    partition_key=dynamodb.Attribute(
        name="booking_id",
        type=dynamodb.AttributeType.STRING
    ),
    billing_mode=dynamodb.BillingMode.PAY_PER_REQUEST,
    point_in_time_recovery=True,
    stream=dynamodb.StreamViewType.NEW_AND_OLD_IMAGES
)

# Grant Lambda permissions
bookings_table.grant_read_write_data(api_function)

Option 2: Amazon RDS (for complex queries)

  • Use Aurora Serverless v2 for auto-scaling
  • Appropriate if need complex joins, transactions, reporting
  • Higher cost, more operational overhead
  • Cold start issues with VPC Lambda

Option 3: Amazon S3 + Athena (for analytics)

  • Store booking records in S3 as Parquet
  • Use Athena for historical analysis
  • DynamoDB for operational data, S3 for archival

Recommended Approach: DynamoDB + S3

  • DynamoDB for real-time booking operations
  • S3 + Glue for data lake (historical analysis)
  • EventBridge rule: DynamoDB Streams → Lambda → S3 (Parquet)

3. Infrastructure as Code & DevOps

Q3.1: Explain your CDK stack design. Why did you separate API and Agent stacks?

Answer:
Stack Separation Strategy:

infrastructure/
├── app.py (CDK entry point)
└── stacks/
    ├── api_stack.py (Lambda + API Gateway)
    └── agent_stack.py (Bedrock Agent + Action Group)

Rationale for Separation:

  1. Independent Lifecycles

    • API changes (code updates) don’t trigger Bedrock Agent redeployment
    • Agent instruction updates don’t require Lambda rebuild
    • Faster, targeted deployments

  2. Resource Dependencies

    • API Stack: Self-contained (Lambda ← Docker image ← ECR)
    • Agent Stack: Depends on Lambda ARN from API stack (optional, if sharing)
    • Clear dependency graph prevents circular dependencies

  3. Team Separation

    • Backend team owns API Stack
    • AI/ML team owns Agent Stack
    • Different deployment permissions

  4. Environment Management

    • Can deploy API to dev but Agent to prod (cost control for LLM)
    • Agent requires Bedrock model access (not available in all regions)

  5. Testing & Development

    • Test API independently via HTTP
    • Test Agent independently via Bedrock console
    • Integration tests combine both

CDK Stack Communication:

# api_stack.py
CfnOutput(self, "LambdaFunctionArn", 
          value=self.api_function.function_arn,
          export_name="TrainBookingApiFunctionArn")

# agent_stack.py (if importing API Lambda)
from aws_cdk import Fn
api_lambda_arn = Fn.import_value("TrainBookingApiFunctionArn")

Alternative Approach (Monolithic Stack):

  • Single stack with all resources
  • Simpler for small projects
  • Slower deployments, tighter coupling
  • Acceptable for personal projects, not for teams

Best Practice: Separate stacks when:

  • Resources have different lifecycles
  • Different teams own different components
  • Need independent deployment cadence
  • Want to share resources across stacks

CDK automatically:

  • Repository name: cdk-<hash>-container-assets-<account>-<region>
  • Configures lifecycle policy (retain last 10 images)

3. Docker Build & Push (during cdk deploy):

}

5. Deployment Optimization:

  • Caching: If Dockerfile/context unchanged, skips build

  • Incremental updates: Only changed layers pushed

Complete Deployment Flow:

  ↓

  ↓
├─ Build Docker image (if changed)
├─ Push to ECR
├─ Create/update Lambda function

Troubleshooting Common Issues:

  1. Docker not running:

    Error: Cannot connect to Docker daemon
Solution: Start Docker Desktop

  2. ECR authentication:

    Error: denied: Your authorization token has expired
Solution: AWS CLI will auto-refresh, ensure aws configure is correct

  3. Platform mismatch:

    Warning: Building on ARM64 Mac for Lambda x86_64
Solution: Specify platform=Platform.LINUX_AMD64 (slower, uses emulation)

  4. Large image size:

    Warning: Image is 2GB
Solution: Multi-stage builds, minimize dependencies

Q3.3: Describe your CDK bootstrapping process. What resources does it create and why are they needed?

Answer:
CDK Bootstrap Purpose:
CDK needs staging infrastructure to deploy assets (Docker images, Lambda code, CloudFormation templates).

Command:

cdk bootstrap aws://ACCOUNT-ID/REGION

Resources Created:

  1. S3 Bucket (cdk-<qualifier>-assets-<account>-<region>)

    • Stores CloudFormation templates
    • Stores Lambda deployment packages (zip files)
    • Versioned for rollback support
    • Lifecycle policy: delete old versions after 30 days

  2. ECR Repository (cdk-<qualifier>-container-assets-<account>-<region>)

    • Stores Docker images for Lambda
    • Lifecycle policy: retain last 10 images
    • Our project uses this for FastAPI container

  3. IAM Roles:

    • CloudFormation Execution Role (cdk-<qualifier>-cfn-exec-role-<account>-<region>)

      • Allows CloudFormation to create resources
      • Principle of least privilege (you define policies)

    • Deploy Role (cdk-<qualifier>-deploy-role-<account>-<region>)

      • Assumed by CDK CLI during deployment
      • Permissions to write to S3, ECR, invoke CloudFormation

    • File Publishing Role (cdk-<qualifier>-file-publishing-role-<account>-<region>)

      • Allows CDK to upload files to S3 bucket

    • Image Publishing Role (cdk-<qualifier>-image-publishing-role-<account>-<region>)

      • Allows CDK to push Docker images to ECR

  4. SSM Parameter (/cdk-bootstrap/<qualifier>/version)

    • Stores bootstrap version number
    • Ensures compatibility between CLI and bootstrap

Bootstrap CloudFormation Template:

Resources:
  StagingBucket:
    Type: AWS::S3::Bucket
    Properties:
      BucketName: !Sub 'cdk-${Qualifier}-assets-${AWS::AccountId}-${AWS::Region}'
      VersioningConfiguration:
        Status: Enabled
      LifecycleConfiguration:
        Rules:
          - NoncurrentVersionExpirationInDays: 30
            Status: Enabled

  ContainerAssetsRepository:
    Type: AWS::ECR::Repository
    Properties:
      RepositoryName: !Sub 'cdk-${Qualifier}-container-assets-${AWS::AccountId}-${AWS::Region}'
      LifecyclePolicy:
        LifecyclePolicyText: |
          {
            "rules": [{
              "rulePriority": 1,
              "selection": {
                "tagStatus": "any",
                "countType": "imageCountMoreThan",
                "countNumber": 10
              },
              "action": { "type": "expire" }
            }]
          }

Why Needed:

  1. Stateful Deployments: CDK needs to store previous deployment state
  2. Asset Management: Large files (Docker images, Lambda packages) can’t be inline in CloudFormation
  3. Cross-Stack References: S3 bucket allows sharing assets between stacks
  4. Security: IAM roles enforce least privilege for deployment operations

Bootstrap Options:

# Standard bootstrap
cdk bootstrap

# Custom qualifier (for multi-environment)
cdk bootstrap --qualifier prod

# With specific trust policies
cdk bootstrap --trust <ACCOUNT-ID> --cloudformation-execution-policies <ARN>

# For CDK Pipelines (CI/CD)
cdk bootstrap --trust <PIPELINE-ACCOUNT> --trust-for-lookup <PIPELINE-ACCOUNT>

Production Considerations:

  1. Multi-Account Setup:

    • Bootstrap each account/region
    • Use different qualifiers for dev/staging/prod
    • Set up cross-account trust for CI/CD

  2. Security:

    • Restrict S3 bucket access
    • Enable S3 bucket encryption (KMS)
    • Use VPC endpoints for private deployments

  3. Cost:

    • Bootstrap resources cost ~$1-2/month
    • S3 storage for templates (minimal)
    • ECR storage for Docker images (varies)

Q4.1: Explain the IAM roles and permissions in your architecture. Apply the principle of least privilege.

Answer:
IAM Architecture Overview:

1. API Lambda Execution Role:

# CDK creates this automatically with Lambda construct
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "logs:CreateLogGroup",
        "logs:CreateLogStream",
        "logs:PutLogEvents"
      ],
      "Resource": "arn:aws:logs:*:*:log-group:/aws/lambda/train-booking-api:*"
    }
  ]
}

Rationale: Only needs CloudWatch Logs for observability. No access to other AWS services.

2. Bedrock Agent Service Role:

agent_role = iam.Role(
    self, "BedrockAgentRole",
    assumed_by=iam.ServicePrincipal("bedrock.amazonaws.com")
)

agent_role.add_to_policy(iam.PolicyStatement(
    effect=iam.Effect.ALLOW,
    actions=[
        "bedrock:InvokeModel",
        "bedrock:InvokeModelWithResponseStream"
    ],
    resources=[
        f"arn:aws:bedrock:{self.region}::foundation-model/anthropic.claude-3-5-sonnet-20241022-v2:0"
    ]
))

Rationale:

  • Only invoke specific foundation model (not all models)
  • No admin permissions on Bedrock
  • Can invoke Action Group Lambda (added via grant_invoke)

3. Action Group Lambda Execution Role:

# Auto-created by CDK, enhanced with:
action_group_function.grant_invoke(agent_role)

# Resulting resource policy on Lambda:
{
  "Effect": "Allow",
  "Principal": {
    "Service": "bedrock.amazonaws.com"
  },
  "Action": "lambda:InvokeFunction",
  "Resource": "arn:aws:lambda:*:*:function:train-booking-action-group",
  "Condition": {
    "StringEquals": {
      "AWS:SourceArn": "arn:aws:bedrock:*:*:agent/<AGENT-ID>"
    }
  }
}

Rationale: Only specific Bedrock Agent can invoke (prevents unauthorized invocations).

4. CDK Deployment Roles (from bootstrap):

  • CloudFormation Execution Role: Can create Lambda, API Gateway, Bedrock Agent
  • Deploy Role: Can write to S3/ECR, invoke CloudFormation
  • File/Image Publishing Roles: Can upload to staging bucket/repository

Principle of Least Privilege Applied:

Component What it CAN do What it CANNOT do
API Lambda Write logs Access DynamoDB, S3, invoke other Lambdas
Agent Role Invoke Claude 3.5 v2 Invoke other models, create agents, delete resources
Action Lambda Write logs, generate PDFs Network access (in VPC), access other AWS services
API Gateway Invoke specific Lambda Access other Lambdas, read logs

Q4.2: What security vulnerabilities exist in the current implementation? How would you address them in production?

Answer:
Current Security Vulnerabilities:

1. No Authentication/Authorization

# Current: Anyone can call API
curl -X POST https://api-url/bookings -d '{...}'

# Vulnerability: Unauthorized bookings, data access

Mitigation:

# Option A: Cognito User Pools
authorizer = apigwv2.HttpUserPoolAuthorizer(
    "CognitoAuthorizer",
    user_pool=cognito.UserPool(self, "BookingUsers"),
    user_pool_clients=[user_pool_client]
)

# Option B: API Keys (for service-to-service)
api_key = apigateway.ApiKey(self, "BookingApiKey")
usage_plan = apigateway.UsagePlan(self, "UsagePlan",
    throttle=apigateway.ThrottleSettings(rate_limit=1000, burst_limit=2000)
)

# Option C: Lambda authorizer with JWT
@app.get("/bookings/{booking_id}")
async def get_booking(booking_id: str, user: str = Depends(get_current_user)):
    # Verify user owns this booking
    if booking.email != user.email and not user.is_admin:
        raise HTTPException(403, "Not authorized")

2. No Input Sanitization for PDF Generation

# Current: User input directly in PDF
passenger_name = "John<script>alert('xss')</script>"

# Vulnerability: Although PDFs are not HTML, special characters could cause issues

Mitigation:

from pydantic import validator, EmailStr

class BookingCreate(BaseModel):

    @validator('passenger_name')

        return v.strip().title()

4. Sensitive Data in Logs

# Current:

# Vulnerability: PII in CloudWatch Logs

Mitigation:

# Mask sensitive data
def mask_email(email: str) -> str:
    parts = email.split('@')
    return f"{parts[0][:2]}***@{parts[1]}"

logger.info(f"Creating booking for {passenger_name}, email: {mask_email(email)}")

# Or use structured logging with filtering
from aws_lambda_powertools import Logger

@logger.inject_lambda_context(clear_state=True)

# Current: Action Group Lambda has no VPC, no HTTPS endpoint

# Vulnerability: Bedrock uses AWS internal network (secure), but no encryption at rest

            Key={'train_number': train_number},

            ConditionExpression='available_seats > :zero',
            ExpressionAttributeValues={':decr': 1, ':zero': 0},
            ReturnValues='UPDATED_NEW'

Q5.2: Explain Lambda cold starts. How would you measure and optimize them for this application?

Answer:
Lambda Cold Start Mechanics:

What Happens During Cold Start:

  1. Download Code (~500ms for Docker image)

    • Lambda pulls Docker image from ECR to execution environment
    • Image cached for ~15 minutes after last invocation

  2. Initialize Runtime (~200-500ms)

    • Start Python 3.13 interpreter
    • Load standard library modules

  3. Initialize Application (~500-2000ms for our app)

    • Import FastAPI, Pydantic, Mangum, ReportLab
    • Execute module-level code
    • Initialize database connections (if any)

  4. Invoke Handler (~50-200ms)

    • Execute actual request logic
    • Only this step occurs on warm invocations

Total Cold Start: ~1.5-3 seconds for our FastAPI container

Measuring Cold Starts:

Method 1: CloudWatch Logs Insights

fields @timestamp, @duration, @initDuration, @message
| filter @type = "REPORT"
| stats 
    avg(@duration) as AvgDuration,
    avg(@initDuration) as AvgColdStart,
    pct(@duration, 50) as P50,
    pct(@duration, 99) as P99,
    count(*) as Invocations
| sort @timestamp desc

Method 2: X-Ray Tracing

Method 3: Custom Metrics

import time

# In Lambda handler

def handler(event, context):

  • SK: GSI1SK = BOOKING#<booking_id>
  • Use Case: Get all bookings for a user
  • Query:
    response = table.query(
    IndexName='GSI1',
    KeyConditionExpression='GSI1PK = :pk',
    ExpressionAttributeValues={':pk': 'USER#john@example.com'}
)

GSI2: Search by Train + Date (Admin)

  • PK: GSI2PK = TRAIN#<train_number>#DATE#<date>
  • SK: GSI2SK = BOOKING#<booking_id>
  • Use Case: Get all bookings for a specific train on a specific date
  • Query:
    response = table.query(
    IndexName='GSI2',
    KeyConditionExpression='GSI2PK = :pk',
    ExpressionAttributeValues={':pk': 'TRAIN#T101#DATE#2025-12-27'}
)

DynamoDB Operations (Python SDK):

1. Search Trains (Query GSI)

import boto3
from boto3.dynamodb.conditions import Key

dynamodb = boto3.resource('dynamodb')
table = dynamodb.Table('TrainBookingSystem')

def search_trains(origin: str, destination: str, date: str):
    response = table.query(
        KeyConditionExpression=Key('PK').eq(f'ROUTE#{origin}#{destination}') &
                              Key('SK').begins_with(f'DATE#{date}')
    )
    return response['Items']

2. Create Booking (Transactional Write)

def create_booking(booking_data):
    booking_id = f"BK{secrets.token_hex(8).upper()}"
    email = booking_data['email']
    train_number = booking_data['train_number']
    journey_date = booking_data['journey_date']
    
    # Transactional write: Create booking + Update train seats
    response = dynamodb_client.transact_write_items(
        TransactItems=[
            {
                'Put': {
                    'TableName': 'TrainBookingSystem',
                    'Item': {
                        'PK': {'S': f'BOOKING#{booking_id}'},
                        'SK': {'S': 'METADATA'},
                        'EntityType': {'S': 'Booking'},
                        'booking_id': {'S': booking_id},
                        'train_number': {'S': train_number},
                        'passenger_name': {'S': booking_data['passenger_name']},
                        'email': {'S': email},
                        'journey_date': {'S': journey_date},
                        'seat_number': {'S': f'A{seat_counter}'},
                        'status': {'S': 'confirmed'},
                        'GSI1PK': {'S': f'USER#{email}'},
                        'GSI1SK': {'S': f'BOOKING#{booking_id}'},
                        'GSI2PK': {'S': f'TRAIN#{train_number}#DATE#{journey_date}'},
                        'GSI2SK': {'S': f'BOOKING#{booking_id}'}
                    },
                    'ConditionExpression': 'attribute_not_exists(PK)'  # Prevent duplicates
                }
            },
            {
                'Update': {
                    'TableName': 'TrainBookingSystem',
                    'Key': {
                        'PK': {'S': f'TRAIN#{train_number}'},
                        'SK': {'S': 'METADATA'}
                    },
                    'UpdateExpression': 'SET available_seats = available_seats - :decr',
                    'ConditionExpression': 'available_seats > :zero',
                    'ExpressionAttributeValues': {
                        ':decr': {'N': '1'},
                        ':zero': {'N': '0'}
                    }
                }
            },
            {
                'Put': {
                    'TableName': 'TrainBookingSystem',
                    'Item': {
                        'PK': {'S': f'USER#{email}'},
                        'SK': {'S': f'BOOKING#{booking_id}'},
                        'EntityType': {'S': 'UserBooking'},
                        'booking_id': {'S': booking_id},
                        'train_number': {'S': train_number},
                        'journey_date': {'S': journey_date},
                        'status': {'S': 'confirmed'}
                    }
                }
            }
        ]
    )
    
    return booking_id

Key Benefits:

  • Atomicity: All 3 writes succeed or all fail (no partial bookings)
  • No Race Conditions: ConditionExpression ensures no overbooking
  • Fast: Single round-trip to DynamoDB

4. Cancel Booking (Transactional Update)

def cancel_booking(booking_id: str):
    # First, get booking to find train_number
    booking = get_booking(booking_id)
    if not booking:
        raise Exception("Booking not found")
    
    train_number = booking['train_number']
    
    # Transactional update: Cancel booking + Restore seat
    dynamodb_client.transact_write_items(
        TransactItems=[
            {
                'Update': {
                    'TableName': 'TrainBookingSystem',
                    'Key': {
                        'PK': {'S': f'BOOKING#{booking_id}'},
                        'SK': {'S': 'METADATA'}
                    },
                    'UpdateExpression': 'SET #status = :cancelled',
                    'ConditionExpression': '#status = :confirmed',
                    'ExpressionAttributeNames': {'#status': 'status'},
                    'ExpressionAttributeValues': {
                        ':cancelled': {'S': 'cancelled'},
                        ':confirmed': {'S': 'confirmed'}
                    }
                }
            },
            {
                'Update': {
                    'TableName': 'TrainBookingSystem',
                    'Key': {
                        'PK': {'S': f'TRAIN#{train_number}'},
                        'SK': {'S': 'METADATA'}
                    },
                    'UpdateExpression': 'SET available_seats = available_seats + :incr',
                    'ExpressionAttributeValues': {
                        ':incr': {'N': '1'}
                    }
                }
            }
        ]
    )

5. Get User Bookings (Query GSI1)

def get_user_bookings(email: str):

        name="SK",

        name="GSI1SK",
        type=dynamodb.AttributeType.STRING
    ),
    projection_type=dynamodb.ProjectionType.ALL
)
