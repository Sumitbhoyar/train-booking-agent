```markdown
# Project Prompt: Train Booking REST API with AWS Bedrock Agent

## Project Overview
Develop a serverless Python train booking system hosted entirely on AWS with minimal infrastructure. The system should expose a REST API via AWS Lambda and API Gateway, use an in-memory database, and integrate with an AWS Bedrock agent for conversational booking management.

## Architecture Components

### Core Infrastructure
- **AWS Lambda**: Host the FastAPI application as a containerized function (supports up to 10GB images)
- **API Gateway**: Use HTTP API (v2) for cost-effective routing and faster performance compared to REST API
- **Amazon Bedrock Agent**: Orchestrate conversational interactions and invoke Lambda functions through action groups
- **Mangum**: ASGI adapter to bridge FastAPI and AWS Lambda's event structure
- **Docker & Amazon ECR**: Package and store the Lambda container image

### Deployment
- **AWS CDK (Python)**: Infrastructure as Code for deploying all components including Bedrock agent, Lambda functions, and API Gateway

## REST API Requirements

### Endpoints to implement
- `GET /trains` - Search available trains by route and date
- `POST /bookings` - Create a new train booking
- `GET /bookings/{booking_id}` - Retrieve booking status
- `DELETE /bookings/{booking_id}` - Cancel a booking
- `GET /health` - Health check endpoint

### Data Model (In-Memory)
```

```
## Bedrock Agent Configuration

### Agent Setup
- **Foundation Model**: Use Claude 3 Sonnet or Claude 3.5 Sonnet for orchestration
- **Instructions**: "You are a train booking assistant. Help users search for trains, make bookings, check booking status, and cancel reservations. Always confirm booking details before finalizing."

### Action Group Definition
Create an action group with Lambda executor that defines the following actions:
- `searchTrains` - Parameters: origin, destination, date
- `createBooking` - Parameters: train_number, passenger_name, email, journey_date
- `getBookingStatus` - Parameters: booking_id
- `cancelBooking` - Parameters: booking_id
```

```
## IAM Permissions Required

### Lambda Execution Role
- Basic Lambda execution permissions
- No additional permissions needed (using in-memory database)

### Bedrock Agent Service Role
- `bedrock:InvokeModel` - To invoke foundation models
- `lambda:InvokeFunction` - To call action group Lambda

### Action Group Lambda Role
- Basic Lambda execution permissions
- Optional: API Gateway invoke permissions if calling the REST API

## CDK Deployment Stack

### Key CDK Constructs
```

```
## Testing Strategy

### REST API Testing
- Use pytest with FastAPI TestClient for unit tests
- Deploy to AWS and test via API Gateway endpoint URL
- Test timeout handling (Lambda max 15 minutes, API Gateway HTTP API max 29 seconds)

### Bedrock Agent Testing
Test through Bedrock Console with sample prompts:
- "Show me trains from Paris to Lyon on December 27th"
- "Book a ticket for John Doe on train T101"
- "What's the status of booking BK12345?"
- "Cancel my booking BK12345"

## Deployment Steps

1. Build and push Docker image to ECR
2. Deploy CDK stack: `cdk deploy --all`
3. Create and prepare Bedrock agent
4. Test REST API endpoints via API Gateway URL
5. Test Bedrock agent interactions through console or SDK

## Cost Optimization Notes
- Lambda charged per invocation and execution time
- API Gateway HTTP API is cheaper than REST API
- Bedrock charged per token for model invocations
- No database costs with in-memory storage
- Suitable for development and low-traffic production workloads

This architecture provides infinite scaling, no server maintenance, minimal downtime, and cost-effective operation for a train booking system.
```
